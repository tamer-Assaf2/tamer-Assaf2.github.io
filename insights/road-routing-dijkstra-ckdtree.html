Building a Road Routing Engine with Dijkstra and cKDTree

A reliable route is the result of a complete spatial pipeline: clean road geometry, a weighted graph, fast endpoint snapping, a shortest-path algorithm, and accurate route reconstruction.

The routing problem is a pipeline

Dijkstra is only one stage of a route engine. Real users provide coordinates, while the algorithm expects valid graph nodes. Real road layers contain multipart lines, crossings, direction rules, duplicated geometry, and disconnected segments. The final result must return GIS geometry rather than a list of abstract node IDs.

  1. 01Prepare road geometry
  2. 02Construct graph nodes
  3. 03Snap input locations
  4. 04Find shortest path
  5. 05Rebuild route geometry

Treating these stages as separate components makes correctness and performance easier to test. It also prevents algorithm success from hiding a broken network model.

Prepare road geometry before the graph

Routing connectivity depends on topology. Roads that visually cross do not necessarily share a graph node, while two endpoints that should connect may differ by a small coordinate tolerance. Before graph construction, define how the source handles intersections, multipart features, duplicate segments, bridges, tunnels, and one-way restrictions.

Work in a coordinate reference system appropriate for the cost model. If edge cost is distance, a projected system with meaningful linear units is often easier to reason about than raw longitude and latitude. Preserve stable identifiers so every graph edge can be traced back to its road feature and geometry.

Convert road segments into a weighted graph

Each valid road endpoint or intersection becomes a node. Each traversable segment becomes an edge. The edge stores a cost and a reference to the original segment used later for route recovery. 

graph[node_a].append((node_b, cost, segment_id))
graph[node_b].append((node_a, cost, segment_id))  # if bidirectional

Distance is the simplest cost, but operational routing may use expected travel time, road class, access permissions, turn restrictions, vehicle limits, or a composite weight. Directionality must be encoded while building the graph. Adding both directions to every segment creates invalid routes on one-way roads.

Use cKDTree for nearest-node search

User coordinates rarely match graph nodes exactly. A spatial index can map each start and destination coordinate to a candidate node. SciPy's cKDTree supports efficient nearest-neighbor queries over node coordinates. 

from scipy.spatial import cKDTree

node_xy = [(x, y) for x, y in nodes]
tree = cKDTree(node_xy)

distance, index = tree.query((input_x, input_y))
nearest_node = nodes[index]

Nearest does not automatically mean valid. Apply a maximum snapping distance, confirm that the node belongs to a routable component, and return a clear error when an input falls outside the supported network. For high accuracy, snapping to the nearest edge and then inserting a temporary node may be better than endpoint-only snapping.

Run Dijkstra and reconstruct the route

Dijkstra's algorithm finds the least-cost path in a graph with non-negative edge weights. A priority queue selects the next node with the lowest known accumulated cost, while a predecessor map records how that node was reached. 

import heapq

queue = [(0, start)]
distance = {start: 0}
previous = {}

while queue:
    current_cost, node = heapq.heappop(queue)

    if node == target:
        break

    if current_cost != distance.get(node):
        continue

    for neighbor, edge_cost, segment_id in graph[node]:
        new_cost = current_cost + edge_cost
        if new_cost < distance.get(neighbor, float("inf")):
            distance[neighbor] = new_cost
            previous[neighbor] = (node, segment_id)
            heapq.heappush(queue, (new_cost, neighbor))

If the target was reached, walk backward through previous to recover the ordered segment IDs, then reverse the sequence. Retrieve the source line geometry, orient segments consistently, and merge or return them as a route feature. Preserve the total cost and snapping distances as result metadata so the route can be validated.

Production considerations

Direction and cost

Model one-way travel, restrictions, units, and the real meaning of the cost function before optimizing the algorithm.

Disconnected networks

Detect components, handle unreachable destinations, and avoid presenting a partial traversal as a valid route.

Reusable indexes

Build the graph and KD-tree once per network version rather than rebuilding them for every request.

Route validation

Check endpoint distance, segment continuity, geometry length, accumulated cost, and known test routes.

Why this architecture matters

A routing engine connects several engineering concerns: GIS data quality, coordinate systems, spatial indexing, graph theory, performance, and API behavior. A clean pipeline allows each concern to evolve independently. For example, a later version can replace endpoint snapping with edge snapping, introduce A*, or move network preparation into a spatial database without rewriting every layer.
