PostGIS for Web GIS: Designing Spatial Databases for Real-World Applications

A spatial database is more than a place to store coordinates. Its geometry model, coordinate systems, indexes, access rules, and API boundaries determine how reliably a Web GIS application behaves.

The role of PostGIS in Web GIS

A Web GIS stack often includes a browser map, an API, background services, and a database. PostGIS gives PostgreSQL native spatial types and functions, allowing geometry-aware filtering, measurement, containment, intersection, and proximity operations to run close to the data.

This matters because application code should not need to download an entire dataset just to answer a spatial question. A well-designed query can return only the records or geometry required for the current map, operation, or user.

Model spatial data deliberately

Use real spatial columns

Longitude and latitude fields can be useful for exchange, but they are not a substitute for a constrained spatial column. A geometry column records the spatial type and reference system directly and enables spatial validation, indexes, and database functions. 

CREATE TABLE stops (
    id          bigserial PRIMARY KEY,
    name        text NOT NULL,
    geom        geometry(Point, 4326) NOT NULL
);

CREATE INDEX stops_geom_gix
ON stops USING GIST (geom);

Treat the SRID as part of the data model

The spatial reference identifier affects every distance, transformation, and overlay operation. Store a deliberate SRID, validate incoming data, and transform at explicit boundaries. Do not silently mix coordinate systems inside the same workflow.

Choose geometry or geography intentionally

The geometry type is usually a strong fit for projected local operations and general GIS interoperability. The geography type can simplify distance calculations over the earth but has different performance and function tradeoffs. The correct choice follows the spatial extent and query patterns, not a universal rule.

Spatial indexes and query design

GiST indexes are a core part of performant PostGIS systems, but an index does not make every spatial expression efficient. Queries should use index-aware predicates, filter early, request only the needed fields, and be reviewed with PostgreSQL query plans. 

CREATE INDEX vehicles_geom_gix
ON vehicles USING GIST (geom);

SELECT id, vehicle_code
FROM vehicles
WHERE ST_DWithin(
    geom,
    ST_SetSRID(ST_Point(:lng, :lat), 4326),
    :distance
);

In a geographic coordinate system, the distance unit and intended accuracy need explicit attention. Depending on the use case, the query may require geography casting or a suitable projected coordinate system.

Queries that belong in the database

Spatial containment, proximity, intersection, aggregation, and bounding-box filters are usually better expressed in PostGIS than recreated across multiple clients. The database becomes the shared implementation for the API, dashboards, scheduled jobs, and other consumers. 

SELECT z.id, z.name
FROM zones z
WHERE ST_Contains(
    z.geom,
    ST_SetSRID(ST_Point(:lng, :lat), 4326)
);

Keep the query contract clear. Define whether points on a boundary count as inside, how invalid geometry is handled, and which result wins when zones overlap. These choices are business rules as much as technical details.

APIs should use parameterized queries, bounded result sets, clear geometry formats, and application-level validation. GeoJSON is useful for browser maps, while vector tiles or simplified geometry may be more appropriate for large datasets and smaller payloads.

The database should enforce durable constraints. The API should enforce request rules and authorization. The client should focus on interaction and presentation. Keeping those responsibilities clear makes the system easier to test and evolve.

Real-time, multi-tenant, and production systems

Bound real-time writes

Separate current state from history when needed, batch frequent updates, and define retention and aggregation strategies.

Enforce tenant scope

Include tenant ownership in keys and indexes, then reinforce it through APIs and PostgreSQL row-level security where suitable.

Validate geometry

Constrain geometry types and SRIDs, check validity, and decide how rejected or repaired geometry is recorded.

Observe query behavior

Monitor slow queries, inspect plans, maintain statistics, and test with realistic spatial distributions and volumes.

Production checklist

  • Use constraints for required geometry types and SRIDs.
  • Create indexes that match real spatial and tenant filters.
  • Parameterize SQL and keep credentials outside source code.
  • Limit geometry detail and result volume at API boundaries.
  • Plan backups, migrations, monitoring, and retention.
  • Test boundary cases, invalid geometry, and mixed projections.
